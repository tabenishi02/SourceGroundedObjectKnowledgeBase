# モデル比較の実行計画

作成日: 2026-10-06。計画段階であり、本書の試験は未実行。

## 目的と現状

モデルだけを変更した比較を行い、Fragmentの忠実さ・網羅性と、検索品質・実行時間・失敗率の違いを判断する。主張数の多さをモデルの優秀さと読み替えない。

現行基準はQwen3.8-27B Q4_K_M、Nomic Embed Text v1.5 Q4_K_M、簡易Reranker `rrf60-literal-v1`、抽出的Final。代表8CaptureのFragment、検索6ケース、Final2ケースは成功済み。ただし初回GPT-OSSとの比較ではPrompt・抽出方式・APIも変わっているため、モデル順位は付けられない。

## 比較の順序

| 段階 | 変更する要素 | 固定するもの | 判断すること |
|---|---|---|---|
| 0 準備・接続確認 | 各モデルのロード | 入力・予算・検証 | 実行可能か、条件を記録できるか |
| 1 Fragmentモデル比較 | 抽出LLM | 全Evidence、Prompt、Schema、SinglePass、引用選択・適応分割 | 忠実さ、網羅性、失敗率、速度 |
| 2 検索モデル比較 | Embedding、次にReranker | 同じ保存済みEvidence/Fragment、query、正解ラベル | 検索順位、遅延、費用対効果 |
| 3 Final比較 | 局所並べ替えLLM | 同じFragment/Cluster・引用・分類 | 情報を落とさない読みやすい順序 |
| 4 組み合わせ確認 | 有望な構成を組み合わせる | 保留データ、採点規則、予算 | 個別の改善が一連の処理でも有効か |

最初からLLM×Embedding×Rerankerの全組み合わせを実行しない。各段階で有望な候補を絞る。

## 0. 比較条件の準備

### データと再現性

- `benchmark/sample-v1.json`の代表8Captureを同一入力の比較用データとして使用する。元manifestを変更せず、今回用のversion付きmanifestを別途作る。
- この8Captureは既にPrompt修正・失敗調査に使った。既存の`test`表示を未知データの証明にせず、今回用manifestでは開発用データとして明示する。
- 未使用Captureを4〜8件選び、公式紹介、百科事典、掲示板、長い表・一覧を含む保留セットを別に作る。転載や同じSourceの別Captureは開発セットと分離し、独立性の不明点を記録する。
- Raw SHA256、Normalized/EvidenceのID・内容hash、Page Context revision、Entity、Prompt/Schema hash、Core commitを固定する。
- 正規化済みの同じ基準DBからモデルごとのDBを作る。他モデルのFragmentを同じ試験入力へ混入させず、旧結果を上書きしない。
- 実ページ本文、gold、DB、Vector、生成結果は`.local/`と`sample/`へ保存し、Git管理外とする。

### LLMの共通設定

| 項目 | 固定条件 |
|---|---|
| 抽出方式 | SinglePass、全Evidence対象 |
| Prompt | high-recall-v4-adaptive-quote-selectionを凍結 |
| 引用 | quote_idを選択しCoreが原文を復元、厳密検証 |
| 入力単位 | 最大480文字、上限到達時に最小120文字まで適応分割 |
| 重なり・再試行 | 現行実装と同じ。子処理全成功時だけ反映 |
| batch / 資料予算 | 1 Evidence / 6000文字、隣接資料の扱いも固定 |
| context / 最大出力 | 16384 / 8192 tokens |
| temperature | 0 |
| reasoning | off。対応しないモデルは別条件として報告 |
| API | LM Studio native APIを共通経路として事前確認 |
| seed | 共通に指定できる場合だけ固定。未対応はnullを記録 |
| 並列度 | 1。別の推論と重ねない |

同じPC・runtimeで1モデルずつ実行する。GGUFファイル名・SHA256・量子化・上流revision・runtime version・GPU/メモリ搭載量と実測使用量を記録する。不明値はunknown/nullとし、CLI commitをruntime versionの代わりにしない。

既存の量子化を使用するので、比較対象は「モデル系列＋量子化＋runtime」の構成である。異なる量子化の結果からモデル本体だけの優劣を断定しない。

Native APIやreasoning offに非対応なら接続不適合として記録する。互換APIやモデル別設定へ黙って切り替えない。代替経路は別の条件IDで測り、共通条件の順位とは分ける。

## 1. Fragmentモデル比較

### 対象

| ID | LLM | 位置づけ |
|---|---|---|
| L01 | Qwen3.8-27B | 現行基準。凍結条件で再測定 |
| L02 | GPT-OSS 20B | 初回モデルを現行条件で比較 |
| L03 | Gemma 4 26B-A4B | Google候補 |
| L04 | Mistral Small 3.2 24B | Mistral候補 |
| L05 | Ministral 3 14B | 小型候補 |
| L06 | Nemotron 3 Nano 30B-A3B | MoE候補 |
| L07 | meta/muse-glimmer | 追加候補 |
| L08 | google/gemma-4-31b-qat | 追加候補 |

保存済み・ダウンロード完了・API対応は試験開始時に再確認する。Phi-4は初期の主抽出比較に混ぜず、後段のReviewer比較用候補にする。

### 実行

1. 事前確認: 引用選択、密度の高い本文、0件理由の3種類の短い固定入力を各モデルで試す。ここでは品質順位を付けず、接続・契約・予算・記録を確認する。
2. 主比較: 8モデル×代表8Captureを各1回、計64ケース。全モデルで同じ検証・再試行・分割上限を使う。
3. 失敗は結果として残す。不正JSONを修復して取り込まず、未完了Captureの候補Fragmentを完成結果と混ぜない。中断・未実行は失敗率の分母と分けて表示する。
4. 暫定上位3モデルを事前に凍結した共通の小規模セットで各3回測り、中央値・範囲と品質のばらつきを確認する。
5. 人間評価後に設定を凍結し、保留セットで確認する。保留結果を見てPromptを変えた場合は、そのセットを以後開発用へ移し、新しい保留セットを用意する。

Promptや方式の改善試験は別の実験にする。SinglePass / MultiPass / Extract+Reviewを比較する場合はLLMを固定し、今回のモデル順位表へ混ぜない。

### 採点

- 自動: Capture完了数、失敗Evidence数、JSON/Schema/引用違反、上限到達・適応分割回数、0件理由、Evidence引用Coverage、Fragment数、重複率、総時間・token数。
- 人間: 根拠に忠実か、主語解決は正しいか、1独立主張か、分類・主張主体・時系列は妥当か。
- 意味評価用のgoldはモデル出力を見る前にEvidenceから作る。各Captureで5 Evidence、計40 Evidenceを固定選択し、主張の多い本文・境界・感想・表・0件候補を含める。選択理由とgold IDを記録する。
- モデル名を隠し、同じ40 Evidenceに関連する出力を全件採点する。全出力を採点できない場合は固定抽出規則と分母を明記する。
- Recallはgold主張の取得率、Precision/Unsupported率は採点した出力主張集合に対する値として報告する。40 Evidenceの評価を全Captureの精度と呼ばない。
- `labels.example.json`のhuman採点経路を利用する。LLM Judgeを補助に使う場合は別列にし、人間goldと同一視しない。

採用は「根拠忠実さ・完了率 → 取りこぼし → 原子性・分類 → 時間・メモリ」の順で判断する。単一総合点だけで決めず、候補間のトレードオフを示す。

## 2. Embedding / Reranker比較

LLMモデルごとのFragment差と検索モデル差を混ぜない。最初は現行Qwenの成功世代を固定したコピーDBで比較する。

### Embeddingを変更する比較

Nomic v1.5、Qwen3-Embedding-8B、BGE-M3、multilingual-e5-large-instruct、Jina Embeddings v4テキスト検索版を対象にする。全文検索・簡易Rerank・query・評価対象を固定する。

モデルに必要なquery/document prefix、pooling、入力上限はそれぞれ正しい設定を使い、モデルと一体の条件として記録する。先頭600文字の共通条件を主比較にし、長文入力対応の評価は別枠とする。各モデルで同じ情報範囲が渡されていることを確認する。

2 Entityにつき12 query、計24 queryを用意する。固有名詞、言い換え、複数条件、時系列・主張種別、関連の薄い検索を含め、開発12 / 保留12に分ける。現在の6検索ケースは接続確認用として残す。

関連性を人間が0/1/2/3で付与する。全候補の上位20件をプールして採点し、各queryのgold範囲を明示する。プールにない関連文書があり得るため、得られるRecallを「プール内goldに対するRecall」と表示する。

指標はRecall@10、MRR、nDCG@10、検索時間。Lexicalのみを共通対照とし、SemanticとHybridを分けて報告する。

### Rerankerを変更する比較

Embedding上位2候補に対し、簡易方式、BGE reranker v2 m3、Qwen3 Reranker 4B / 8Bを比較する。モデルごとに再検索せず、同一の候補上位50件とqueryを入力にする。候補集合に含まれるgoldの割合と、その中の順位改善を分ける。

専用BGE/Qwen Reranker adapterとスコア取得経路は未実装。API対応を確認してからadapterを用意し、未対応を低品質の測定結果と混同しない。

## 3. Final Document比較

現行の抽出的FinalはLLMを使わないため、これを8モデルで実行してもLLMの差は測れない。

同じFragment・分類・Cluster・引用を固定し、次を別々に比べる。

| 条件 | 処理 | 比較対象 |
|---|---|---|
| D00 | 抽出的階層生成 | 共通の対照。1回だけ生成 |
| D01〜D03 | `llm_order:true`による局所並べ替え | Fragment比較の上位3 LLM |

既存Cluster IDの完全な順列だけを許す。材料24 Cluster / 8000文字の局所予算を固定し、全Fragment保持・引用保持を自動検証する。人間はFacet内の順序、見出し間の流れ、情報を見つけやすいかをモデル名を隠して比較する。

並べ替えは重複削減や文章の圧縮ではない。現行Finalの長大化を解決したと扱わない。要約・文章生成・重複統合モデルを比較したい場合は、情報保持を検証できるwriter方式を別途設計する。

Reviewer比較は、上位抽出LLM単独と同じLLM＋Phi-4を同じ資料で比べる別枠にする。Phi-4とPhi-4 reasoning-plusは同じモデルとして扱わず、実際に取得したモデルIDを固定する。

## 4. 組み合わせの最終確認

個別比較後、次の最大4構成を同じ保留データで通す。

| 構成 | Fragment LLM | 検索 | Final |
|---|---|---|---|
| C00 基準 | Qwen3.8-27B | Nomic＋簡易Rerank | 抽出的 |
| C01 品質候補 | 上位LLM 1 | 上位Embedding＋上位Reranker | 抽出的、並べ替えは別条件 |
| C02 速度候補 | 忠実さを満たす高速LLM | 低遅延の検索構成 | 抽出的 |
| C03 代替候補 | 上位LLM 2 | C01と同じ検索構成 | C01と同じFinal条件 |

上位モデル・構成は試験結果を見てから確定する。現時点で勝者や推奨組み合わせを決めない。

## 予想される実行時間

### 見積もりの根拠

現行Qwen3.8-27B Q4_K_Mの適応分割試験は、代表8Captureの開始から最後の推論完了まで約18395秒（5時間7分）。8モデルが同程度の速度なら、主比較64ケースだけで約40.9時間になる。根拠runは`75838054-5cff-407b-9ae9-92c839134f0d`。最終batchだけの時間合計は途中の処理・再試行を含まないため、全体見積もりには使わない。

以下は事前測定前の計画用概算。同じPCで1モデルずつ実行し、主にGPU上で推論できること、データ量が現行と同程度であることを前提とする。未知のモデルの速度を実測済みとは扱わない。

| 段階 | 機械の処理時間の目安 | 計算・前提 |
|---|---:|---|
| 0 ロード・短い入力での事前確認 | 1〜3時間 | 8モデル、各3種類。接続・ウォームアップ・再試行を含む |
| 1 主比較 | 20〜85時間 | 基準約41時間。モデル別速度・適応分割による差を約0.5〜2倍で仮置き |
| 1 上位3モデルの反復 | 4〜15時間 | 3モデル×3回。固定小規模セットは代表8Captureの処理量の1/4以下と仮定 |
| 2 Embedding比較 | 0.5〜6時間 | 同じ約1万Evidence/Fragmentを5モデルで処理し、24 queryを比較 |
| 2 Reranker比較 | 1〜10時間 | 2 Embedding×4方式×24 query×50候補、計9600組を上限に比較 |
| 3 Final比較 | 2〜8時間 | 2 Entity×3 LLMの局所並べ替え。抽出的対照の生成は短時間 |
| 4 組み合わせ確認 | 5〜40時間 | 最大4構成×保留4〜8Capture。Fragment量を現行に近いと仮定 |
| **機械処理の合計** | **約35〜170時間** | 連続稼働で約1.5〜7日。計画上は約60〜90時間を中心目安とする |

今回のNomic再検証から全Embedding候補の時間を推定しない。既存Vectorを再利用した工程を含むため、新しいEmbeddingでは100件を試して「全対象件数÷100×100件の処理時間」で補正する。Rerankerも固定候補の小規模実測から補正する。

### 人間の作業時間と日程

機械処理とは別に、gold作成・採点・結果確認は暫定で30〜100時間程度を見込む。40 Evidenceのgold作成を各10〜20分とすれば約7〜13時間。8モデル×40 Evidence×平均10〜20主張を1主張20〜40秒で採点すると約18〜71時間となり、これに検索の関連性ラベルとFinalの抜き取り比較が加わる。主張密度が高い場合や複数人で採点する場合はさらに増える。

機械処理を夜間にも継続し、人間の作業を1日8時間とした場合、全段階の完了は概ね1〜3週間を作業日程の目安とする。データ準備と機械処理を一部重ねられるが、各段階の候補選定は人間評価の完了後に行う。まず段階0〜1を実施し、実測値と採点件数から後続段階を再見積もりする。

モデルのダウンロード、保留Captureの収集、未実装adapter・runnerの開発、API非対応やCPU offloadへの対処、PCの他用途による停止時間は上記に含めない。これらを含む完了日は現時点で保証しない。試験中に遅い構成が見つかった場合は打切り条件を別途決め、未完了・打切りを成功と表示しない。

## 実行・出力・完了条件

- モデルごとに独立したrun IDとDBを持つ。同一条件だけresumeし、Prompt・モデル・データ変更時は新しいrunにする。
- モデルロード成功を確認してから独立したバックグラウンド処理を起動する。PID、run ID、状態確認コマンドを記録し、自動ポーリングは行わない。
- Raw不変、DB整合性、外部キー、他モデルの出力混入なしを確認する。ロード/OOM/API不適合/契約違反/出力上限/意味上の問題を別の失敗種別にする。
- 1条件1回を予備測定とし、精密な速度順位は反復測定後に示す。ウォームアップ、モデルロード時間、実推論時間、Embedding生成時間は別々に記録する。
- 結果は`sample/モデル比較/`へ日本語テキストとCSVで出力する。構成一覧、試験条件、Capture別結果、意味評価の分母、速度・使用量、代表例、未実行・失敗理由を含める。
- 完了とは、対象条件に結果または未実行理由がそろい、人間が同じ入力の差を追えること。全モデル成功を無理に要求せず、失敗も比較結果に含める。
- 上記の概算を事前確認で得た実測値から更新する。主比較は8×8=64 Fragmentケースで、密集Captureの適応分割が時間を増やす。所要時間と停止条件を確認してから本試験を起動する。

実行前に必要な作業: 今回用manifestと未使用保留データ、40 Evidenceのgold、query/関連性gold、モデル別条件台帳、固定入力の事前確認runner、Reranker adapter、比較exportを準備する。既存CLI/benchmark/採点経路を利用し、不足分だけ追加する。本書作成ではモデル推論・ダウンロード・追加adapter実装は行っていない。
