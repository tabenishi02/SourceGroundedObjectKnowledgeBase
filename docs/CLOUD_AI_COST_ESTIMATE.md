# クラウドAI利用の合理性と費用試算

確認日: 2026-10-06。OpenAI Docsスキルで公式API料金を確認し、Anthropic公式料金と合わせて試算した。クラウドへ実データを送信せず、API利用・課金は行っていない。

## 判断

クラウドAIは選択肢として合理的。ただし、速度を理由に全件をOpus等へ切り替える判断はまだできない。
現在の遅さは1038回の逐次呼び出しと大量のJSON出力によるため、Providerを変えるだけで高速化する保証はない。クラウド利用の利点は独立した入力の並列処理、モデル品質による再試行削減、ローカルGPUを占有しないこと。実際の速度・品質・費用は未検証。
少量・非緊急ならローカル中心、速度が必要なら低価格クラウドモデル、難しい入力や失敗だけ高性能モデルへ送る方式を比較するのが妥当。

## 試算条件

- 実データ8CaptureのQwen評価: 入力4769210 token、出力1942948 token、1038リクエスト。失敗・再試行も含む。
- 同じtoken数をクラウドで消費する仮定。tokenizer・推論token・出力量・再試行回数の違いにより、実際の請求は変わる。これは確定請求額でも上限でもない。
- Standardの短い入力に適用される通常料金。全リクエストの合計入力が477万tokenでも、各リクエストを長いcontextとして扱う意味ではない。
- キャッシュ割引なし。画像・Web検索・クラウドEmbedding・Finalの追加LLM処理・税・為替手数料・開発費を含めない。Capture/Import/検索/既定の抽出的Finalはローカルに残す。
- 日本円は便宜上1 USD = 150円。現在の為替レートとして引用していない。

計算式: `費用USD = 入力token数 / 1000000 × 入力単価 + 出力token数 / 1000000 × 出力単価`。
月額は今回と同じページ構成で5件/日×30日=150件、8件の費用×18.75とする。ページ構成が重い方へ偏ると増額する。

## モデル別費用

GPT-6.1 Solの8件費用は入力約$9.54・出力約$19.43で、約67%が出力費用。入力cacheだけでは全体を大幅には削減できず、出力形式のコンパクト化にも意味がある。

## 割引と費用の振れ幅

OpenAI BatchとClaude Message Batchesは通常APIの50%割引を提供する。[OpenAI Batch](https://developers.openai.com/api/docs/guides/batch)、[Claude Batches](https://platform.claude.com/docs/en/build-with-claude/batch-processing)。同じ処理量なら上表の約半額で、Sol約2173円、Opus約4345円/8件。
Batchは最大24時間の処理枠であり、即時の高速化を約束するものではない。適応分割や失敗時の再試行は前段の結果に依存するため、複数Batch段階になると全体が24時間を超える可能性がある。期限切れ・未処理は成功としない。

クラウドで入力・出力とも1.5倍になれば、Sol約6518円、Opus約13036円/8件。2倍なら各約8690円・17381円。これは感度計算で、1.5倍が安全な上限という意味ではない。
OpenAIの推論tokenは出力として課金される。[公式推論ガイド](https://developers.openai.com/api/docs/guides/reasoning)。APIのusageで請求対象の出力全体を測り、表示された本文だけで予算管理しない。

ローカル＋高性能クラウドを併用し、全体のtoken処理量の10%だけをSolまたはOpusへ送るなら、月150件のクラウド部分は約8147円・16294円。ローカル電力等は別。10%はページ数の割合ではない。今回のように重い少数ページへ費用が集中する場合、難しいページだけの送信でも想定以上になる。

## 速度の見込み

クラウド速度は測定していない。以下は同じ1942948出力tokenを生成する数学的な感度計算で、モデル別予測ではない。入力処理・通信・推論追加・再試行・API待ち・DB処理を含めない。

| 仮の1リクエスト生成速度 | 逐次の生成時間 | 独立入力8並列を常時維持できた理想時間 |
|---|---:|---:|
| 100 tokens/s | 約5.4時間 | 約40分 |
| 200 tokens/s | 約2.7時間 | 約20分 |
| 400 tokens/s | 約1.35時間 | 約10分 |

現行Qwenの実データ生成速度中央値は約119 tokens/s。クラウドがこれより遅ければ逐次のままでは速くならない。上表の並列値を保証時間にしない。
例えば8並列×200 tokens/sには出力だけで毎分96000 tokenの処理能力が必要で、入力・request数にもアカウントの制限がある。適応分割の依存関係や終了間際の並列数低下もある。実アカウントのrate limitと実データ総時間を測って判断する。

## 採用案

1. Capture・Raw・DB・検索・引用検証はローカルへ残し、送信可能な本文の抽出だけをクラウド候補にする。ログイン情報・私的ページを無条件に送る設計にしない。
2. 同じ小規模EvidenceでローカルQwen、GPT-6 Luna、GPT-6.1 Sol、Opusを比較し、総時間・実請求token・成功率・人間の主張goldを確認する。小規模試験は$10～20程度のアプリ側予算枠から始め、上限で中断できるようにする。
3. 品質が維持できれば低価格モデルを標準にし、失敗・難しい入力だけSol/Opusへ送る。全件Opusは高い人件費や緊急性に見合う用途で検討する。
4. 現行の出力重複・上限時再試行も改善する。クラウド化だけでは巨大なFinalや人間の確認負担は解消しない。

既存benchmarkはlocalhostのみを許可する設計。クラウド試験は明示的に別の実行経路・送信範囲・予算を設け、既存のローカル試験制約を無断で解除しない。
今回の作業は費用・合理性の調査だけ。Provider変更や外部送信は実施していない。
