# Knowledge Pipelineの改善案

作成日：2026-10-07。根拠：[試験で判明した問題点](PIPELINE_TEST_FINDINGS.md)。本書は提案であり、以下の機能は未実装。

## 推奨する方針

**網羅的な保存資料は保持し、利用する主張について根拠を確認した上で、用途に適した情報を出す。** 全Fragmentの再抽出や生成LLMによる全面的な要約を最初の対策にはしない。まず、主張と引用の対応・帰属を見えるようにし、支持確認の評価事例を作る。その後、表示候補を中心とした意味検証、概要の必要項目による選択、出典表示の縮約へ進む。

## 問題ごとの候補と推奨案

| 問題 | 候補 | 推奨案・理由 |
|---|---|---|
| Q01 支持不整合 | 語の一致検査／全件LLM検証／対象を限定したLLM検証と人間の評価 | 決定的な出典整合性検査に、限定的な意味検証を追加。語の一致だけでは否定・伝聞を判定できず、全件検証はまず費用対効果を測る必要がある |
| Q02 帰属・解釈 | 本文の自動書き換え／表示時の帰属ラベル／抽出分類の再評価 | 先に帰属ラベルを表示し、分類の誤りは別の評価記録へ残す。原文を無断で書き換えない |
| Q03 対応追跡 | 本文へ全ID・引用を埋め込む／短い参照と監査付録 | 短い参照から支持Fragment・引用・世代を辿る。説明可能性を上げながら本文予算を確保する |
| V01・V02 概要の選択 | facetルール追加／用途別の必要項目／LLMによる自由要約 | 必要項目を軸にした選択を採用し、既存ルールは候補探索に使う。自由要約は新たな意味変化を招くため後回し |
| F01 完全Finalのサイズ | 完全資料の削除／出典共有化／監査資料と閲覧資料の分離 | 完全資料を保持し、閲覧・質問用資料を分ける。出典共有化は表示の別形式として追加する |
| R01 検索精度 | モデル変更／query追加だけ／正解付き質問試験 | まず必要Claim・Evidenceをラベル付けした質問試験。精度が測れないままモデルを変更しない |
| O01 停止・復旧 | 無制限再試行／エラー別の有限再試行／常に手動復旧 | エラー別の有限再試行と独立した状態管理。検証失敗とGPU障害を分ける |
| M01 計測 | 全8Captureの再実行／代表条件の反復／既存累積値だけで判断 | 改善した工程を代表条件で反復し、意味品質確認後に本試験へ拡大する |

## 1. 主張の支持確認：Q01

### 二段階で確認する

第一段階では、Evidence・Snapshot・正規化世代・引用範囲が一致し、引用がその入力内に存在することを決定的に確認する。支持する最小限の引用と、必要な前後文脈を別に保持する。引用範囲は保存済みの本文を基準にした位置とhashで特定し、後の表示用正規化で位置を変えない。

これは意味的な支持を保証しない。第二段階で、主張の主体、述語、否定、時期、伝聞元、強さが引用に支えられているかを評価する。語の一致・数値差などは疑わしい候補の検出に使い、正しい言い換えや照応を機械的に拒否する唯一の条件にはしない。

### 最初は小さな評価集合から始める

30〜50件を目安に、支持あり・支持なし・判断困難の例を人間がラベル付けする。人物紹介の引用で制作方針を主張する例、否定の反転、伝聞の事実化、時期の混同、主語の取り違え、複数主張の混在、正しい言い換えを含める。件数は最初の動作評価の目安で、網羅的な精度証明ではない。

その集合で判定promptを固定してから、実Viewに表示する候補を中心に検証する。同じEvidence内の複数候補は小さくまとめ、Claim・引用・文脈・判定器versionのhashで結果を再利用する。抽出に使ったLLMと同じモデルを判定に使う場合、別の呼出でも誤りが相関する可能性があるため、人間の正解と照合する。

### 判定と保存を分ける

- 判定は `supported / unsupported / uncertain`、未実施は `unreviewed` とする。モデルのsupportedは「機械判定で整合」と表示し、真実性や人間の確認済みを意味しない。
- 生のFragment・Claim・完全Finalは保存する。判定結果は別のversion付き記録にし、判定者・モデル・prompt・入力hash・理由・支持範囲を残す。
- 利用用Viewでは、支持不足を確認した主張を確定情報として出さない。未確認・判断困難な主張を含む監査表示と、支持確認を通った利用用表示を区別する。確認できない必要項目は「資料不足／要確認」とし、別の付属情報で埋め合わせない。
- 検証対象が表示候補だけなら、完全Finalの残りを検証済みとは扱わない。

再試行では、主張と引用のどの要素が合わないかを具体的に返す。修正候補の生成と支持判定を別の記録にし、修正した文章を未検証のまま採用しない。機械的に弱い言葉へ置き換えて合格とする対処は採らない。

受入条件：既知の支持不整合を検出でき、正しい言い換えも保持できること。支持なしをsupportedとする誤受理、支持ありを拒否する誤拒否、uncertainの割合を別々に報告する。小さな評価集合での誤受理0件は初期の通過条件とし、全件の安全性の証明とはしない。

既存Schemaは厳密なため、引用範囲や判定状態を既存のLLM出力へ無造作に追加しない。まず別の監査記録で導入し、生成契約を変更する場合だけSchema・prompt・algorithmを新versionにする。

## 2. 帰属と対応関係を表示する：Q02・Q03

本文はClaimの内容を保持し、隣接する表示に「資料の記述」「資料筆者の評価」「発言者の説明」「CPCの推論」「支持未確認」などを出す。既存の`fact`を「外部的な真実の認定」と読ませない。分類と帰属は別の軸であるため、article_author由来を一律にsource_interpretationへ変換しない。

本文の短い参照番号から、Claim ID、支持Fragment ID、実引用、Evidence ID、Snapshot、正規化・抽出世代、支持判定へ辿る監査付録を作る。複数支持がある場合はすべて保持し、同じEvidenceから異なる引用を使うFragmentも区別する。

受入条件：ユーザーが指摘したような2つの主張について、別Fragment・別世代であることを出力から判別できること。資料の評価や伝聞を本文だけ読んでも確定事実と誤認しにくいこと。表示変更によってClaimの本文・支持を改変しないこと。

## 3. 「重要そうなfacet」から「概要に必要な項目」へ：V01・V02

| 対象 | shortで優先する項目 | standardで広げる項目 | detailedで広げる項目 |
|---|---|---|---|
| Character | 定義・登場作品、立場や所属、人物像 | 基本プロフィール、主要な関係、特徴と背景 | 個別エピソード、能力、作品内の変化、受け止められ方 |
| Work | 何の作品か、ジャンル、中心的な体験や仕組み | 制作・提供、対象媒体、基本構成、開始時期 | 展開・個別システム・イベント・関連作品 |
| Concept | 定義、目的、他の概念と区別する特徴 | 適用範囲、構成、代表的な例 | 例外、歴史、論点、類似概念との関係 |

各項目に対応する候補を既存facetルールで探し、支持・対象一致を確認してから選ぶ。重要項目が見つからない場合は欠落を明示する。未知のEntity typeでは共通の定義・目的・特徴へfallbackする。必要項目の単なる数合わせではなく、実際に対象を説明できるかを評価する。

shortでは必要項目へ先に予算を割り当て、standardはその基本情報を維持して広げ、detailedは細部へ進む。同義の複数主張は選択上の重複を抑えるが、時期・帰属・否定が異なる主張をまとめて同一視しない。相反する基本情報がある場合は片方を黙って選ばず、相違を示す。

この段階は既存Claimの選択・配列を中心にする。自然な概要文への統合は、意味保持を評価できてから別条件で検討する。Claim選択の改善と、LLMによる新しい文章の生成を混同しない。

予算は、閲覧用の簡潔な本文・参照と、AIへ実際に渡す構造化入力をそれぞれ測る。監査付録を全量AI入力へ付けて予算を隠さない。実tokenizerを使えない場合は現在の保守的尺度を明示する。

受入条件：shortが定義と主要項目を説明し、付属情報だけにならないこと。standard/detailedで追加された情報と省略理由が分かること。Character・Work・Conceptのラベル付き事例で、重要項目の充足と根拠保持を確認する。

## 4. 完全Finalは保持し、出典を共有する：F01

現在の完全Finalと構造化資料は互換性・監査のために保持する。その上で、同じEvidence・Snapshot・引用範囲を共有出典として短い参照番号へまとめる「閲覧版」を追加する。元のFragment支持の対応表は失わない。主張と時系列で同じ説明を繰り返す代わりに、閲覧版では必要に応じて参照先を示す。

通常閲覧は概要Viewから始め、詳細が必要な箇所はClaim・出典へ辿る。AIの質問対応は検索した関連Claim・Fragmentと必要なEvidenceを予算内へ詰める。完全Finalの全量投入を既定にしない。

受入条件：全支持へ辿れ、帰属・時期・相違が保持されること。完全資料の大きさと閲覧版の大きさを別々に報告すること。削減率を先に成功条件とせず、資料としての有用性を確認すること。

## 5. 検索を質問に対して評価する：R01

初期集合は20〜30質問を目安にする。Entity名だけでなく、人物像、作品の仕組み、関係、時期、評価の帰属、矛盾、答えが資料にない質問、同名・類似語の取り違えを含める。

正解は必要Claimと支持Evidenceへ付ける。検索対象にEvidenceとFragmentが混在するため、同じ答えを異なるIDで持つ結果を正答として対応付けられる評価単位を定義する。必要項目Recall@k、順位、不要・誤対象の混入、資料不足の認識を確認する。query付きViewへ詰めた後に必要情報が残るかも評価する。

同じ質問でlexical/semantic/hybridを比較し、baselineを確立してからrerankerやEmbeddingモデルの変更を検討する。テスト質問は調整用と保留用に分け、改善を保留用でも確認する。小さな集合への過適合を避ける。

## 6. エラー別に復旧する：O01

- 接続断・一時的なサーバー障害：上限回数と待ち時間を設定した再試行。GPUエラーの場合はローカルサーバーの健康状態を確認し、既存runtime条件が一致する場合だけ再開する。共有サーバーを無条件に再起動しない。
- Schema違反：既存の有限再試行を利用し、不正フィールド・対象ID・必要値を具体的に返す。
- 支持不整合：接続障害として繰り返さない。修正候補または人間の確認へ回す。
- 出力上限：失敗windowだけを再分割する。単に上限を増やし続けない。

独立した実行プロセスに、工程・window・完了数・失敗分類・累積時間を記録する。再開は入力とruntime、生成・判定versionを照合する。終了・要確認を通知し、再試行終了を「処理中」のまま放置しない。

受入条件：人工的な接続断・形式違反等で成功済み結果が重複生成されないこと、有限回数で停止して理由が残ること、復旧後に未完了だけを再開できること。スリープ後のGPU復旧は実機確認として別に記録する。

## 7. 品質と速度を分離して測る：M01

まず意味品質を小さな評価集合で確認する。速度は短い入力・長い入力をそれぞれ、固定条件でwarmup後3回程度測り、中央値・範囲・token・失敗数を記録する。cold start、cache再利用、障害復旧は別条件として報告する。工程時間と端から端までの経過時間も分ける。

意味検証の追加時間は実測する。抽出・検証・検索・表示のどこへ追加されたかを記録し、以前の累積値だけから検証の時間を推定しない。確認済みの結果を再利用し、表示候補の検証から必要に応じて対象を広げる。

## 実装順序と移行

1. 支持対応・帰属の監査出力と、意味品質の評価集合を追加する（Q01〜Q03）。
2. 判定器を小さな集合で校正し、表示候補に限定した支持確認を導入する（Q01）。
3. 必要項目によるView選択と、実用queryの検索・View評価を行う（V01・V02・R01）。
4. 完全資料と互換な閲覧版・共有出典を追加する（F01）。
5. 有限復旧・通知・固定条件の反復試験を整える（O01・M01）。

既存Raw・Fragment・Claim・完全Finalは上書きせず、判定・閲覧用派生物を追加する。既存データは初期状態をunreviewedとし、過去の処理成功を支持確認済みへ自動変換しない。新しい選択・判定versionを記録し、戻す場合は旧Viewを選択できるようにする。意味品質が未確認の旧出力へ戻した場合、その確認状態も保持する。

最初の実装範囲は1と2の小規模な評価までを推奨する。全候補のモデル比較・全Captureの再抽出・自由要約の追加を同時に始めず、支持確認が改善したかと追加コストを確認してから拡大する。
