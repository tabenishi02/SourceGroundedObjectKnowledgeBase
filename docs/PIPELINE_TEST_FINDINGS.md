# Knowledge Pipeline試験で判明した問題点

整理日：2026-10-07。対象：代表8Captureの再抽出比較V2、後段処理の前後試験、概要優先Viewの再生成、およびユーザー指摘のClaim・Fragment・Evidence照合。

## 全体評価

再抽出16ケースと後段の前後8工程は完了した。Raw・元の比較DB・Fragmentの保持と、試験用DBの整合性・外部キー検証は合格した。後段は変更後の工程時間合計で約108秒となり、処理時間そのものは実用的な範囲にある。

しかし、**処理完了・Schema適合・引用の存在・DB整合性は、意味の正確さや情報の網羅性を保証しない**。引用と主張の不整合が少なくとも1例確認されており、意味品質の受入は未完了である。ユーザーによる「Fragmentに致命的な問題は見つからなかった」という当初の入力確認を、後から見つかった不整合も含めて全件合格と解釈しない。

## 問題一覧と対応状況

P0は正確性の受入を阻害する問題、P1は利用時の誤解・選択品質・運用停止に関する問題、P2は測定や改善判断の制約を表す。本表は優先度の提案であり、追加実装の完了宣言ではない。

| ID | 優先度 | 問題 | 状態 |
|---|---|---|---|
| Q01 | P0 | 引用が存在しても主張を支持しないFragmentを受理する | 不整合の実例確認済み、意味的な支持検証は未実装 |
| Q02 | P1 | 記事の評価・解釈が断定的な事実に見える | 表示・分類の課題として未解決 |
| Q03 | P1 | Evidence IDだけではどのFragment・引用を選んだか分からない | 対応追跡はDBで可能、View表示は不足 |
| V01 | P1 | 概要に必要な情報より付属的な情報が先に選ばれる | 概要優先ルールを実装・再生成済み。汎用性は未評価 |
| V02 | P1 | Viewの情報量・網羅性とmodeの役割が利用目的に合わない | 部分改善。質問に必要な情報の受入試験は未実施 |

## Q01：引用の存在確認と、主張の支持確認が別になっていない

変更前の実Fragmentに、制作方針とインタビュー由来の説明を主張している一方、`original_text`は人物紹介とスカウト経緯で、該当するインタビューの記述を含まない例があった。ローカルDBで主張と引用を照合して確認した。

このFragmentでは本文に複数の主張も含まれる。`atomic_claim=true`というモデル出力だけでは、本当に1件1主張であることは保証できない。

現在の検証はSchema、対象Evidence、入力内に引用が存在すること等を確認する。引用の文章が主張の主体・述語・否定・時期・帰属を十分に支持するかは検証していない。このため、Schema上は正しくても意味的に不適切なFragmentがClaims・Finalまで伝播し得る。

変更後には同じ制作方針について、インタビューを含む別の引用を持つFragmentが存在する。ただし、この1例の改善をもって全件の支持整合性が確認されたとは扱わない。不整合の発生原因が分割外本文の混入だけであったとも、今回の対応照合だけでは断定できない。

対応候補：支持する具体的な引用範囲を明示することに加え、主張と引用の意味対応を評価する。まず否定・伝聞・主張主体・時期・複数主張を含む回帰ケースを用意する。意味判定にLLMを使う場合も、判定と生成を区別し、失敗を自動的に合格へ書き換えない。

受入条件：根拠のない主張が選択・公開用Viewに進まないこと、支持不足の理由を記録できること、正しい言い換えを過剰に拒否しないことを、ラベル付き事例で確認する。

## Q02・Q03：帰属と対応関係が表示から伝わらない

ユーザーが比較した制作方針のFragmentと、短いViewに選ばれた性格のClaimは、同じEvidence IDを参照するが別のFragmentであり、さらに変更前・変更後の抽出世代も異なっていた。

Claimの支持テーブルを確認すると、Viewの性格の主張は変更後の別Fragmentと同文で、その引用には該当の性格表現がある。したがって、**この例は制作方針のFragmentをViewが別の意味へ書き換えた事例ではない**。これは一般に意味保持が保証されたという結論ではなく、今回の対応関係についての確認である。

一方、ViewにはClaim ID・Evidence ID・Snapshotはあるが、支持Fragment IDと実際の引用が直接表示されない。このため、同じEvidenceから抽出された別の主張や世代差を見分けにくい。

また、記事の人物評が`fact`と断定文で表示されると、metadataに`article_author`があっても、読み手は確定した設定・事実と受け取り得る。以前の限定的な比較でも、本文にあった「主張されている」という帰属表現が変更後に薄れた例を確認した。引用中に同じ言葉があることと、その評価を客観的事実として扱ってよいことは別である。

対応候補：Claim → 支持Fragment → 実引用 → Evidence → Snapshot・抽出世代を表示上も辿れるようにする。評価・伝聞・解釈の帰属を本文または隣接表示で明示する。`fact`分類の妥当性は意味品質の評価対象とし、記事由来というだけで機械的に全件を同じ分類へ変更しない。

## V01・V02：重要度の選択と、予算に収まる情報の質

初期ViewはClaim IDの順とfacet・情報種別の巡回に依存し、短い資料の先頭へスキル・楽曲・二次創作等が入り、人物や作品の概要を説明できなかった。modeの予算は異なっていたが、重要な情報から補足へ広げる意図が不足していた。

`cbcaa19`で概要優先の選択を追加した。対象自身の定義・所属・性格・ジャンル等を優先し、同義facetの反復より異なる基本項目を先に選ぶ。修正版はCharacterのshort/standard/detailedで5/16/31 Claim、Workで4/13/28 Claimとなった。ユーザーは改善後の方がよいと評価している。

残る問題は、facet・subjectによるルール判定が汎用的な意味理解ではないこと、異なる話題をバランスよく選んでも必要情報が揃うとは限らないこと、出典やmetadataが予算を消費して選択件数が小さいことである。予算のcounterはUTF-8バイト数による保守的尺度であり、実モデルのtoken数ではない。

対応候補：人物・作品・概念の概要に必要な項目を受入事例として定義する。実際の質問に対するquery付きViewも評価する。表示用の簡潔な出典参照と、完全な監査情報を分ける設計を検討する。

## F01：網羅的Finalの使い方とサイズ

変更後FinalはCharacter 505,133文字、Work 3,841,869文字、合計4,347,002文字。出典脚注部分はそれぞれ約72.59%、63.05%を占める。主張の時系列での再掲も長さに影響する。

ユーザーは網羅的な内容自体をよいと評価しているため、完全資料を捨てて短文化する方針にはしない。監査・詳細確認・別View再生成の基盤として保持し、通常閲覧はView、質問対応は検索と関連するFragment/Evidenceを使う方針を整理した。

残る設計課題は、共有出典の短い参照と詳細監査への分離、必要部分へ辿る閲覧導線、質問用資料の組み立てである。利用方針の文書化は、これらの閲覧UIや自動連携の実装完了を意味しない。

## R01：検索の意味品質と情報網羅性が未評価

前後各6ケースでlexical/semantic/hybridの動作を確認した。全ケースで10件取得し、各結果から元Evidenceへ参照できた。しかし、試験queryはEntity名を中心としており、質問への答えが上位に含まれるか、言い換えに対応するか、不要な結果を避けるかは評価していない。正解ラベルがないためRecall/MRR/nDCGは未評価である。

Fragment総数は変更前5,337、変更後5,356と近いが、意味品質の維持を証明しない。substantive Evidenceの参照は513/647から510/647へ減少した。完全一致も表現・facet・metadata差を含む指標であり、意味的なRecall/Precisionの代わりにならない。

対応候補：概要・属性・関係・時期・伝聞/評価・矛盾を問う実用queryを用意し、必要なClaimと支持Evidenceをラベル付けする。変更前の出力を無条件に正解として扱わない。

## O01：抽出処理の停止と復旧

試験中に出力上限、AssessmentとFragmentの矛盾、SchemaにないFragmentフィールド、GPUタイムアウト・エンジン終了による停止が発生した。成功済みの結果を保持して再開し、最終的に全ケースは完了したが、複数回の確認・再試行が必要だった。

- 分割外の全文が`metadata.content`から入力へ混入する問題は、`4d14b48`で入力を対象windowに限定する修正を実施した。
- FragmentがあるのにEvidenceを除外する矛盾は、`7551812`で再試行診断にEvidence IDと必要値を明示した。検証基準は緩めていない。
- 変更前の余分な`type`フィールドによる失敗は、比較条件を保った再試行で回復した。
- GPUタイムアウト後は同じ設定でモデルを再ロードし、未完了分を再開した。スリープが原因だったという因果関係の厳密な再現試験はしていない。

再開機能の有効性は確認済みだが、無人運用の安定性は未確立。対応候補は、障害分類、回数制限付き再試行、終了・失敗の通知、未完了の可視化であり、形式・意味の検証を省略することではない。

## M01：計測結果の解釈に制約がある

再抽出の累積時間は約6時間56分から4時間42分へ32.2%短縮した。ただし、成功済み結果の再利用、診断修正、サーバー再ロード、失敗・復旧のコストを含む運用評価で、全条件を独立反復した純粋な速度試験ではない。失敗attempt数166→14も、実装だけによる改善率とは扱わない。

後段は同じ現在の実装に前後のFragmentを与えた比較であり、旧後段と新後段の実装比較ではない。工程合計120.2秒→108.0秒はサービス起動・確認・全体経過時間を含まず、単発の順序・cache・負荷の影響を切り分けていない。増分Embeddingの実データ試験は入力不変での全件再利用を確認したが、入力変更時の無効化をこの試験で改めて実証したわけではない。
