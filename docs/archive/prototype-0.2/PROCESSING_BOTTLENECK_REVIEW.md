# 処理時間の原因調査と改善案

> **Archived / Historical** — Rename前のPrototypeの記録です。旧名称・コマンド・パスは当時の事実を保持しており、現行操作は[README](../../../README.md)を参照してください。

調査日: 2026-10-06。実装変更・追加推論は行わず、実データSQLiteを読み取り専用で調査した。
対象はQwenの代表8Capture run `75838054-5cff-407b-9ae9-92c839134f0d`と[速度再試験](MODEL_SPEED_PREFLIGHT_RESULTS.md)。

## 結論

主因は推論の遅さだけではなく、小さな入力に対して詳細なJSONを大量に逐次生成する構成。DBや検索の高速化より、再試行を整理し、同じ意味情報を少ない出力tokenで表現することを優先する。
現行約5.1時間を数分にする根拠はない。品質を維持した改善は、まず重複処理と不要な出力の削減を実測で積み上げる。

## 計測方法

`extraction_batches.ai_run`はバッチの最後のAI実行しか示さないため、これだけの合計は分割中・再試行中の時間を落とす。
今回は各最新extraction jobの開始時刻と次job開始時刻を区切りとして、`ai_runs`のhigh_recall_fragment全実行と`ai_observations`を集計した。最後のケースは推論が終了した区間まで。全文や個人情報は報告へ複製しない。
durationはHTTP応答待ちを含み、GPUの純粋な演算時間ではない。CPU/GPU割当やcache状態の原因まではこの記録から確定しない。

| 項目 | 集計値 |
|---|---:|
| AI呼び出し | 1038回 |
| AI応答待ちの合計 | 18378秒、約5.11時間 |
| 全体に占めるAI応答待ち | 99%以上 |
| 入力token合計 | 4769210 |
| 出力token合計 | 1942948 |
| 成功AI実行 | 959回 |
| 失敗AI実行 | 79回、約35.4分 |
| JSON解析エラー | 56回、約8.4分 |
| 出力8192 token到達 | 23回、約27.0分 |
| validation_error付き再試行 | 71回、約14.9分 |
| 再試行でも8192 tokenに到達 | 8回、約9.3分 |
| API生成tokens/s中央値 | 約119.2 |

失敗時間と再試行時間は重なりがあり、合算して削減可能時間としない。失敗をなくしても約35分の全額がそのまま削減されるとは限らず、代わりの正常処理にも時間が必要。

## 時間が増える仕組み

1. **出力の詳細さ。** Promptは高Recallの全主張列挙と出典ごとの重複保持を要求する。各Fragmentで分類・主張主体・時間文脈・引用ID等を繰り返し出力する。今回、737 Evidenceから5246 Fragmentを生成し、成功出力だけでも1715825 token。主張を削らずに表現を小さくする余地がある。
2. **細かい分割と逐次呼び出し。** `capture.py`は原則480字、最大64字重なりでwindowを作る。文境界でさらに短くなり、出力上限時は240字・120字へ再分割する。1038回中529回は入力本文240字以下。それぞれにPrompt、Schema、背景文脈を送り、応答を待つ。小さいwindow自体は上限回避に必要だったため、単純に拡大すると既存の失敗が戻る。
3. **出力上限に対する不要な再試行。** `_extract_window()`はValueErrorを一度同じwindowで再試行し、2回失敗してから`extract_window()`で分割する。既に予算到達が確定した入力をもう一度生成し、8回は再び8192 tokenに達した。
4. **JSON形式をPromptだけで指示。** `Application.call_llm()`はSchemaをPromptに付けるが、現行Native ProviderはAPIの制約付き生成へSchemaを送らない。JSON後の説明文等で解析が失敗し、再生成が必要になる。予備試験のGemmaも同種の問題を示した。
5. **入力の反復。** 各windowでSchema・Page Context・neighborsを送り、本文はevidenceとquote_choicesのtextにも含まれる。入力token中央値は4697。今回の主因は累計応答待ちだが、入力表現の共有・簡略化も候補になる。cacheの実効状態は不明。

ケース07・08だけでAI応答時間の約71%を占めた。軽いページを改善するより、長く主張が密集したページへの対策を先に比較するのが効率的。
DB保存・Python検証・その他の時間は全体の小部分であり、DBのリファクタリングやハードウェア交換を第一の対策にする根拠はない。

## 改善案と優先順位

| 優先 | 改善 | 見込む効果 | 品質維持の条件 |
|---|---|---|---|
| 1 | 出力上限エラーは同じwindowで再試行せず直ちに分割 | 今回の「再試行も上限」8回約9.3分が回避候補。分割後処理は依然必要 | 同じ本文全体を子windowで処理し、引用・全Evidence評価を維持 |
| 1 | Schemaで制約するJSON生成経路を追加比較 | JSON解析失敗・subject null等の形式違反を減らす候補 | 互換API条件を別記録。Schema制約後も引用・意味検証を続ける |
| 2 | LLM応答だけをコンパクトにし、Coreが現行Schemaへ復元 | 多数の反復key・既定null等の出力を減らし、上限到達も抑える候補 | 不明な時期はnullとして復元。主張・分類・主張主体・引用を省略しない。DB契約は維持 |
| 2 | 成功しやすい入力量を事前に選択 | 大きなwindowを失敗させてから分割する費用を減らす | 本文長だけでなく既存出力密度を使う。全文coverageを確認 |
| 2 | 短く疎なEvidenceだけを適切にまとめる | 小さい呼び出し数と反復Promptを減らす | 出力予算からwindowを決定。単にbatch_sizeを増やしても480字で再分割されるため不十分 |
| 3 | window単位で成功をcheckpointし、同条件の結果を再利用 | 中断・部分失敗時に成功済みwindowを再推論しない | 内容hashだけでなくEntity・背景文脈・Prompt・Schema・モデル・設定をキーにする。異なる出典との対応は残す |
| 3 | GPT-OSSを実データで比較 | 予備S03は約188.5 tokens/s・形式適合3/3で有望 | Qwenと同じ意味的coverage、引用、再試行率で比較。推論low・出力量の違いを含めて総時間を測る |

LM Studioは`/v1/chat/completions`でJSON SchemaによるStructured Outputを提供する。[公式仕様](https://lmstudio.ai/docs/developer/openai-compat/structured-output)。モデル・Schema・runtimeの対応と速度は実機で確認する必要があり、Native APIと同じ結果になるとは仮定しない。

出力tokenを30%減らせた場合、単純な比例計算では5.1時間から約3.6時間になる。ただし入力処理・再試行・制約付き生成の負荷が変わるため、これは感度計算であって達成予測ではない。現段階で2倍以上の高速化を保証しない。

## 抽出以外の改善

- **Final:** 現在は生成自体より、長い出典本文を引用ごとに再表示して約50万字・378万字になることが問題。出典本文を一度だけ付録へ置き、各主張から参照する表示と短い概要を作る。出典・異なる主張・矛盾は保持し、人間の確認負担を減らす。抽出時間を直接減らす対策ではない。
- **Embedding:** 現行`Application.embed()`は対象候補全体を再生成する。モデル空間・内容hash・data_versionで未更新分を選び、変更分だけ生成する。保存済みVectorは検索で再利用する。
- **検索:** 現行はPythonで候補Vector全体のcosineを計算する。現在約1万件の規模では抽出より優先度が低いが、件数増加時はVector索引の比較と検索時間の計測が必要。
- **並列化:** 同一GPUへ大量に並列要求すると必ず速くなるわけではない。まず出力・重複費用を減らし、少数並列と逐次を同じ内容で比較する。多GPUやruntime設定による改善は実測なしに断定しない。

## 推奨する確認手順

まず「上限時の即時分割」と「制約付きJSON」を独立した変更として比較する。次にコンパクト出力、最後に入力単位とモデルを比較する。
軽いケース04・中規模06・重い08を固定し、元の結果を残す。総時間、全AI呼び出し時間、入力/出力token、失敗・再試行・分割数を記録する。
合格条件は引用の厳密一致、全Evidence評価、Raw不変、DB整合性に加え、人間が固定した主張の取りこぼしと根拠なし追加が悪化しないこと。Fragment数が減っただけでは改善と判定しない。
品質維持を確認した変更だけを代表8Captureへ広げる。今回は提案までで、コード修正や再実行はしていない。
