# 実運用の処理時間見積もりと運用可能性

評価日: 2026-10-06。[速度予備試験](MODEL_SPEED_PREFLIGHT_RESULTS.md)と、現行Prototypeの実データ評価を根拠にした。同じPCでモデルを逐次使用する前提。新しい推論・性能試験は実行していない。

結論: 個人が少量の資料を蓄積し、抽出を夜間にまとめる運用は条件付きで可能。一方、Capture直後に完全な結果を求める対話運用、毎日大量のページを処理する運用、人がFinal全文を読んで確認する運用は、現状のままでは現実的でない。

## 作業ごとの時間

| 作業 | 現在の規模での目安 | 根拠・制約 |
|---|---|---|
| ChromeでCapture、ZIP保存 | 1件数秒～数十秒を暫定計画枠とする | 時間実測なし。ページ・画像・MHTML・ZIPサイズ・保存先に依存。成功確認済みでも秒数を保証しない |
| ZIP Import、正規化、Evidence作成 | 通常ページ1件数秒～数十秒を暫定計画枠とする | LLMを使わない決定的処理。専用時間計測なし。大量・巨大ページには適用しない |
| LLMロード | 約7～46秒/モデル | 今回の実測。通常は常駐させ、毎Captureの処理時間には加えない |
| Fragment抽出（Qwen） | 実データ1件約1.6～143分、8件約5.1時間 | 分割・再試行を含む既存run。平均約38.3分、中央値約18.9分 |
| Embedding構築（Nomic） | 約1万件なら1～5分を計画枠 | 前回の約10314件では、workerログ作成から検索run開始まで約55秒。ロード・起動・Embeddingを含むファイル時刻の粗い観測で、専用の処理時間計測ではない。長い本文・別モデルは未推定 |
| 検索用queryのEmbedding＋検索 | 1 query約1～10秒を計画枠 | 既存6検索ケースと報告処理が約29秒以内。個別queryの実測ではなく、検索モード・対象数で変わる。索引構築を含めない |
| 現行の簡易Reranker | 上記検索時間に含む | RRF順位と文字列一致を使う処理。学習済みRerankerモデルは未評価で、同じ時間とはみなさない |
| 現行Final Document作成 | 1 Entity数秒を計画枠 | 2 Entityの生成・報告・比較exportが約4秒の区間内。LLMなしの抽出的構成。個別の厳密なdurationではない |
| LLMによるFinal並べ替え・要約 | 未推定 | 現行既定FinalはLLMを使わない。予備試験はFragment抽出用で、この工程の時間に流用できない |
| 人間の確認・修正 | 機械処理と別枠。全件確認は長時間 | 下記参照。品質goldがなく、速度だけでは検証作業を省けない |

暫定計画枠は実測値ではない。Capture・Importの秒数と個別検索の時間を必要とする運用SLAは、別途測定して確定する。

| 01 | 約16.4分 |
| 02 | 約10.4分 |

| 04 | 約1.6分 |

8件から737 Evidence・5246 Fragmentを生成した。長いEvidence、主張数、重なりのあるwindow、上限到達後の再分割が待ち時間を増やす。単一の約480字入力が12秒で返っても、ページ全体が12秒で終わるわけではない。

## モデルを変えた場合

S03の中央値による、予備試験と同種の入力を10回逐次処理する時間。ロードを含めず、入力や出力量が変わる実ページへの換算ではない。

| Qwen3.8-27B | off | 約2.0分 | 3/3 | 約5.1時間（実データ基準） |
| GPT-OSS 20B | low | 約1.0分 | 3/3 | 未確定 |

## 日常運用の処理量

Qwenで今回の8件と同じ混合比のCaptureを処理すると仮定する。これは抽出時間だけであり、人間の確認、待機列、モデル切替、Embedding等は追加になる。

| 新規Capture数 | 抽出の単純概算 | 運用評価 |
|---|---:|---|
| 1件/日 | 平均約38分。ただし大型は2時間超 | バックグラウンドなら可能。Capture直後の完成待ちは困難 |
| 5件/日 | 約3.2時間 | 夜間8時間枠に収まりやすい |
| 10件/日 | 約6.4時間 | 夜間枠に近い。余裕30%を加えると約8.3時間で、重いページが続くと翌日へ繰り越す |
| 20件/日 | 約12.8時間 | 夜間8時間のみでは待ち行列が増える。常時運転も人間確認が追いつくか別途評価が必要 |
| 100件の初回一括処理 | 約64時間 | 連続約2.7日、夜間8時間なら約8夜。大型資料が偏る場合はさらに延びる |

8時間枠の理論値は約12.5 Capture。処理時間に30%の余裕を見込むと約9.6 Captureだが、ページ差が大きいため最初は5件/日程度を計画上限とし、実績で調整する。これは運用案で、現行システムにキュー制御や夜間スケジュールが実装済みという意味ではない。

現行`Application.embed()`はフィルタで指定した現行世代の候補をすべて再Embeddingし、未処理分だけを自動抽出する実装ではない。全体の再EmbeddingをCaptureごとに実行すると、蓄積量に応じて重複処理が増える。検索は保存済みVectorを使うので、queryごとに全件Embeddingし直す必要はない。
現行Semantic検索はSQLiteからVectorを読み出し、Pythonで全候補のcosineを計算する。約1万件での応答目安を10万・100万件へそのまま適用できない。

## 人間の負担と実用性

現行FinalはCharacter約499334字、Work約3778450字。仮に毎分500～1000字で通読すると、前者約8～17時間、後者約63～126時間。これは仮定に基づく読書時間で、根拠を照合する時間はさらに必要。
5246 Fragmentを1件20～40秒で全件採点すると約29～58時間。日常運用で全件精読する設計は、機械処理が速くなっても続けにくい。

| 想定用途 | 評価 |
|---|---|
| Rawを先に保存し、数件/日を夜間抽出、翌日検索する個人利用 | 条件付きで現実的。失敗の再開・未完了の表示、処理量制限、人間の抜き取り確認が必要 |
| 保存済み資料を検索し、必要な根拠を部分的に読む | 現在の規模では現実的な候補。検索の品質と個別応答時間は未確定 |
| Capture後数秒～数分でページ全体の抽出結果を使う | 重い実ページでは困難。保存完了と解析完了を分ける必要がある |
| 毎日20～100件を夜間だけで全量抽出する | 今回の処理量では非現実的。増え続ける未処理キューへの対策が必要 |
| Final全文を毎回読んで承認する | 非現実的。既定表示を短くし、詳細・引用を必要時に展開する設計が必要 |
| 品質を自動保証して無人公開する | 判定不能。人間goldがなく、形式適合は意味的品質の保証ではない |

運用を始めるなら、実データ成功実績のあるQwenを暫定基準に、少量・非同期・翌日利用・検索中心にするのが妥当。速度改善の優先候補はGPT-OSSの実データ比較、負荷改善は変更分のEmbeddingと抽出重複の抑制、利用改善はFinalの要約表示と根拠への参照。これらは提案であり、本見積もりでは実装していない。
